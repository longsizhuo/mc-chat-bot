# Product Roadmap · mc-chat-bot

> 这是一份激进的产品路线图，不是技术愿景书。每个 milestone 都可以被砍掉。

**核心判断（写给所有人看，包括自己）**：

这个项目现在的问题不是功能不够，是**没有用户**。3 人 MC 服务器 + 几个固定 DF 群友 = 实验室产品。
技术架构（三层、memory 系统、五步加游戏）已经超前于实际用量。接下来要反转优先级：**先让外部人跑起来，再完善框架**。

---

## M1：让第一批陌生人能装上并跑起来（目标：2 周内）

**核心 KPI**：GitHub Stars 从当前基线 +30，README 点进来能在 30 分钟内跑通的比例 > 50%（用 Issue 里的"装不上"数量倒推）。

### 1-1. 脚手架命令真实可用

**痛点**：README 写着"加新游戏 = 复制 1 个文件夹"，但没有命令行工具，实际上要手动 cp + 改 8 个地方。外部开发者看完文档还是不知道从哪下手。

**可衡量目标**：`python -m gamebot.create_game <name>` 一条命令生成完整的 stub——包括 `bridge.py`、`prompt.md`、`README.md`、`config.example.yml` 片段。生成后 `python run.py` 不报错。

**实现成本**：1 天。不需要设计，照抄 `df/` 目录结构写模板字符串就够了。

### 1-2. NapCat 联动 openInvest：抽出共享 qq_bridge 包

**痛点**：`gamebot/core/qq_bridge.py` 和 openInvest 里的 QQ 接入代码是两份独立维护的相同逻辑——CQ:at 解析、群名片缓存、多群路由。任何一处 bug 要改两遍。

**可衡量目标**：把 `gamebot/core/qq_bridge.py` 发布为本地可 pip install 的包（暂时不上 PyPI，用 `pip install -e ./qq-bridge/`）；openInvest 切过来；mc-chat-bot 也切过来；两个项目的 QQ 消息收发行为不变。

**为什么现在做**：这是 TODO.md 里已经明确要做的事，而且越晚做，两份代码分叉越严重，迁移成本线性增长。

**kill criteria**：openInvest 的 QQ 接入在 M1 期间没有任何新需求 → 推迟到 M2 做，先稳 mc-chat-bot 自身。

### 1-3. 一键 Docker 部署

**痛点**：现有文档要求用户自己安装 Python 3.10+、配置 RCON、配 NapCat。每一步都是劝退点。外部用户（尤其是 MC 服主）不是开发者，他们只会 `docker run`。

**可衡量目标**：`docker compose up` 拉起完整 stack（gamebot + NapCat + 一个最小化 MC 服），能在 QQ 群里发"你好"收到小方回复。Compose 文件进仓库，不需要任何额外配置步骤。

**实现成本**：2 天。风险：NapCat 的扫码登录在 Docker 里交互性不好，需要挂卷持久化 session。

### 1-4. 对外传播：一篇真实的"我用这个给 3 个人的 MC 服装了 AI 管家"博客

**痛点**：`involutionhell.com/docs` 有文章入口但没曝光。GitHub 的技术内容要靠外部流量来。

**可衡量目标**：在少数派 / V2EX / 掘金发文（三选一），带 GitHub 链接，1 周内带来 GitHub Stars > 20。文章核心卖点：`[CMD:...]` 标签这套 tool-use 比 JSON output 稳定得多——这个才是外部人看了会心动的点。

**kill criteria for M1**：2 周结束时 GitHub Stars 增量 < 10 → 说明内容定位有问题，M2 前必须重新诊断（不是继续堆功能）。

## M2：DF 数据深化 + 第三个游戏落地（目标：1 个月内）

**核心 KPI**：DF 群的日活消息中 bot 参与率 > 30%（当前估计 < 10%，因为 cookie 经常过期导致功能断档）；第三个游戏模块有至少 1 个真实外部用户在跑。

### 2-1. DF cookie 自动续期或告警降级

**这是最核心的留存问题，没有之一。**

**痛点**：DF 的 cookie 几小时到几天就过期，一旦过期，bot 的核心功能（战绩查询）全部失效，但群里用户只会看到沉默或报错——不是优雅降级而是直接崩掉。用户体验最差的时刻恰好是最需要 bot 的时候。

**可衡量目标**：cookie 过期时 bot 主动推群消息"战绩查询暂时不可用，密码播报不受影响"；同时实现 cookie 有效性定时探活（每 1 小时 ping 一次接口，失败就告警）。后续可接入自动抓包脚本（复杂度高，M3 再说）。

### 2-2. DF 多用户 RoomId 跨账号匹配

**痛点**：当前只有一份 cookie（龙龙的），只能看到龙龙视角的战报。队友的视角（他们在哪张图亏损、他们的撤离率）完全看不到。群里其他玩家没有被 bot 服务到，天然流失。

**可衡量目标**：支持多个群友各提交自己的 cookie（通过私聊 bot 一条命令完成注册）；bot 按 RoomId 把多份战报关联成一张队伍级视图；"上把我们打的咋样"返回所有有 cookie 的人的视角。

**隐私设计**：cookie 只存本地，不上传，不共享原始数据，只共享聚合结论。在群里明确说明。

**实现成本**：中等。`scripts/df_stats/` 已经支持多套 curl 路径，扩展成动态加载不难。难点在 RoomId 对齐逻辑。

### 2-3. 第三个游戏：接《原神 / 星穹铁道》——不是王者、不是 CS

**为什么不是王者荣耀**：王者的 API 封闭程度和三角洲一样，但用户群体更大 → 竞争对手更多，差异化更难。

**为什么不是 CS2 / Valorant**：Steam API / Riot API 开放，但目标用户群（英文社区）和本项目（中文 QQ 群）错位。短期没有真实用户场景。

**为什么是米哈游游戏**：
1. `enka.network` / `hoyolab` API 公开，社区维护的 Python 库（`genshin.py`）成熟。
2. 用户已经在 QQ 群里问"我今天该刷什么副本"——这个问题可以被 bot 回答。
3. 米哈游的 daily check-in、树脂、副本 CD 都有时间敏感性 → 定时播报有真实价值（不只是被动问答）。
4. 和 DF 一样是"单向助手"（游戏内没有 API）——可以直接复用 DF 模块的架构，`games/gi/` 照抄 `games/df/` 结构。

**可衡量目标**：`games/gi/` 模块实装，支持：①今日树脂/洞天宝钱状态查询；②每日副本提醒；③角色圣遗物评分（调 `enka.network`）。至少 1 个外部用户（非本人）在自己的 QQ 群里跑通。

**kill criteria for M2**：DF cookie 续期问题在 M2 期间没有解决 → 禁止开发原神模块，所有资源先修 DF 的核心体验问题。功能广度不能以牺牲现有用户体验为代价。

### 2-4. memory 系统的战略意义变现

**痛点**：现在 memory 系统技术上已经完整（SPO 三元组 + FTS5 + 剪枝），但 AI 真正利用它的场景还很少——除了 alias 顺藤摸瓜之外，"战术习惯学习"和"高光局自动归档"都还是 TODO。

**可衡量目标**：DF bot 在 5 局战报之后能主动说一句"你在巴克什亏损 3 次了，建议换图"——这是 memory 系统的杀手级应用，也是任何竞品都没有的。实现：每次 `df_match` 后自动写 episode；`df_advice` 调用时把最近 20 条 episodes 注入 context。

## M3：framework 开放生态 + 增长飞轮（目标：3 个月内）

**核心 KPI**：GitHub 出现至少 3 个不是本人维护的游戏模块 fork / PR；框架从"一个人的玩具"变成"有人愿意贡献的开源项目"。

**现实判断**：M3 的目标完全依赖 M1/M2 是否带来了真实用户。如果 M2 结束时外部用户为 0，M3 的生态目标就是空话——应该直接 pivot 到"纵深做好 MC + DF"而不是横向扩张。

### 3-1. 框架真正的"5 步指南"可执行化

**痛点**：文档说"加新游戏 = 5 步"，但这 5 步里有"在 `gamebot/games/mc/bot.py` 实例化"——这要求贡献者读懂现有代码。真正的"5 步"应该是：运行一条命令，改一个配置文件，改 prompt.md，完成。

**可衡量目标**：有外部开发者在没有任何沟通的情况下，只靠 README + `python -m gamebot.create_game` + CLAUDE.md，在 2 小时内接入一个新游戏的 skeleton。验证方法：找一个不认识的开发者做用户测试，记录卡点。

### 3-2. AI provider 运行时切换 + A/B 测试框架

**痛点**：现在切 LLM（DeepSeek vs Claude vs Ollama）需要改 config 重启。但不同游戏场景对 LLM 的需求不同——MC 盖房子需要长上下文，DF 战报分析需要数学推理，每日密码解析不需要 LLM 完全不需要消耗 token。

**可衡量目标**：config 支持 per-game provider 配置（MC 用 Claude，DF 用 DeepSeek R1，GI 用 Ollama 本地）；运行时可以通过 QQ 群管理员命令热切换 model（不重启）。

### 3-3. 发布 PyPI 包 `qq-onebot-bridge` + 写贡献者文档

**可衡量目标**：`pip install qq-onebot-bridge` 可用；有至少 1 个项目（除 mc-chat-bot 和 openInvest 外）依赖它；CONTRIBUTING.md 里有完整的"如何提 PR 加新游戏"指南（而不只是 CLAUDE.md 给 AI agent 看的技术规范）。

### 3-4. 增长策略：不靠功能靠场景

**三个可执行的传播打法，不要四个：**

1. **短视频**：录一个 60 秒视频——群里发"帮我盖一栋六层豪宅"，MC 游戏里 AI 真盖了。这是唯一能让非开发者也看懂价值的格式。投 B 站/抖音技术区，不需要剪辑，原始录屏就够震撼。

2. **开发者社区植入**：找 MC 服主社区（MCBBs 论坛、国内 MC 论坛），主动回复"我想给服务器加个 QQ 群 AI 助手怎么做"类帖子，给项目链接。精准触达最有动力的用户。

3. **AI 生成内容的二次传播**：每周让 bot 自动把"本周 MC 服务器编年史"发到博客（`involutionhell.com/docs`），这是 AI 生成的真实内容，有 SEO 价值，也给项目一个持续的"存活信号"。

**kill criteria for M3**：M3 结束时（3 个月后，即 2026-08）GitHub Stars < 50 且外部贡献者 = 0 → 停止框架推广方向，聚焦做好 MC + DF 两个游戏的深度，不再接新游戏。这个项目的核心价值变成"一个家庭/小圈子 QQ bot 套件"而不是"开源框架"。接受这个结果，不强行续命。

## 优先级总结

```
M1 脚手架命令 + Docker            ★★★★★  直接影响外部人能否用起来
M1 博客传播                       ★★★★★  没有外部流量，后面都是空的
M1 qq_bridge 包                   ★★★★☆  技术债，越晚越贵
M2 DF cookie 告警                 ★★★★★  现有用户留存，最基础的事
M2 多用户 RoomId                   ★★★☆☆  增加 DF 群内覆盖面，复杂度中等
M2 原神/铁道模块                   ★★★☆☆  新用户场景，依赖 M1 有外部用户
M2 memory 变现                    ★★★★☆  唯一的真差异化，必须做
M3 PyPI 包 + 贡献文档             ★★★☆☆  生态前提是先有用户
M3 A/B 测试框架                   ★★☆☆☆  锦上添花，M1/M2 做不好就砍
```

---

*最后说一句*：三层架构做完了，memory 系统做完了，LLM 静默失败治理了。这些都是**正确的事**，但现在的瓶颈不在代码质量——在于有没有人用。接下来 1 个月，每一行新代码都要先问：**这能带来几个用户，或者留住哪个现有用户？**
