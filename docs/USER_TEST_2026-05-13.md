# 用户体验测试报告

**测试人**：18 岁大学生，平时玩网易版多，Java 版用 HMCL，不懂服务器运维
**测试日期**：2026-05-13
**进入方式**：朋友甩了个 GitHub 链接说"看看这个"

---

## 第一部分：假装我第一次翻开这个 GitHub 项目

### 30 秒内能不能懂这是干嘛的？

**能，而且很快。**

第一行就是：
> 把 QQ 群和游戏打通：群里发一句话，游戏里立刻执行；游戏里死了挂了升级了，QQ 群里实时推送。

这句话我秒懂。下面那张表格列了"群友说给钻石 → 游戏真给了"，直接 get 到了。

配合那个截图文案（左边 QQ 发"给我钻石"，右边游戏执行了），第一印象打 9 分。

**核心卖点"QQ↔游戏双向桥接"说清楚了没有？**

说清楚了，而且清楚得出乎意料。README 写的"双向桥接是这个项目的核心——市面上要么是游戏内 AI、要么是 QQ bot，把这俩串起来形成连续上下文的不多见"，这句自我定位我看了是认可的，听起来不是在吹，是真的想到位了。

### 想不想部署来玩玩？

坦白说——想，但是劝退点也不少，具体说。

## 第二部分：我是 DF 玩家被拉进 257381453 群

### 群里那个 bot 给你的感觉

挺期待的。功能表里列了：拉战绩、战术建议、每天 06:00 自动出密码、别名注册。

密码那个功能是真的香。DF 每天地图密码很多群友都在问，有个 bot 早上自动发出来省了多少事。这个是我看完之后觉得最实在的功能之一。

**教练人设是不是真的"教练"还是装的？**

这里我有点保留意见。README 说"教练人设，system prompt 在 prompt.md，不动代码就能改 AI 性格"。

问题是，教练这个人设依赖的是 AI 分析战绩数据，而数据从腾讯接口来，腾讯接口本身就有限制（README 里也说了"nickName 永远是空字符串"，靠别名表识别队友）。如果数据本身就残缺，AI 分析出来的"战术建议"能有多靠谱我持怀疑态度。

说白了：用几局数据告诉我"你撤离率偏低，建议换图"，这不是教练，这是 Excel 读数据。真正的教练会看你打仗的决策，这个 bot 做不到。所以教练人设有一点点过度包装，功能实际上更像"数据播报员"，这已经很有用了，但别叫教练。

### 哪些功能是真有用 / 哪些是过度设计

**真有用：**
- 每天自动发密码——实打实的刚需
- "我玩牧羊人"注册别名——说一句就完事，我愿意发
- `@MCBot 上把怎么样` 拉战报——随手查，比自己打开 APP 看方便

**过度设计（感觉）：**
- "排除法识别队友"——3 人开黑 + 已注册 alias 反推未识别队友。听起来很聪明，但实际上我打 DF 经常和随机匹配的人一起玩，这个推理会准吗？感觉误判概率很高，然后 bot 信心满满叫错名字，比没有功能更尴尬
- "Agent memory SPO 三元组"——这是给开发者吹的，群友完全感知不到，存不存在都无所谓

### 注册别名顺不顺手？多少群友会真去发？

"我玩牧羊人"这句话注册别名，挺顺的。但问题在于：DF 这个游戏大部分玩家随机干员的，"我玩牧羊人"这事要先有一批固定玩某干员的群友，bot 才有意义。

我估计一个 20 人的 DF 群，愿意主动发注册消息的可能有 5-8 个人，剩下的人懒或者无所谓。功能没问题，但普及率取决于群氛围，不是 bot 的问题。

cookie 要抓包这个事，群里大多数人根本不知道怎么搞，这个门槛要在群置顶里写清楚，不然有时候数据拉不到，bot 就傻了。

## 第三部分：我是 MC 玩家进 mc.involutionhell.com

### 跟小方说话的体验，我期望什么

我进 MC 服，在聊天框里打"小方 给我 64 个钻石"，我期望的是：
- 1-3 秒内回我，东西到手
- 回话有点人味，不要太机器人腔调
- 如果做不到，直接说做不到，别沉默

从 README 展示来看这三点基本做到了。"好的，给你 64 钻石！"简洁，操作执行了，这个感觉就对。

但我很好奇失败的情况。如果我说"帮我在旁边盖个 6 层别墅"，AI 开始一块一块 setblock，中途服务器卡了或者 AI 生成了奇怪的坐标，会发生什么？README 没有说错误处理，这个我隐约有点担心。

盖房子功能我觉得是整个项目里最吸引人的卖点，但也是最容易翻车的。真的能稳定盖出来吗？那个截图的"6 层豪宅"是真实 ingame 照片还是摆拍的？

### 死亡吐槽 85 条，会不会很快重复腻？

老实说，**会的。**

85 条按 16 种死因分，每种平均 5 条，服务器玩久了就会开始背下来。苦力怕吐槽第 3 次还行，第 20 次大家就无感了。

这个不是问题，是正常产品生命周期。但如果想做得好，可以让 AI 动态生成死亡吐槽（根据玩家名字、死法、地点、最近发生的事情），这样每次都不一样。现在是静态文案库，能用，但天花板明显。

周日 22:00 古风战报、周一死亡集锦，这些定时推送我觉得比死亡吐槽更有可持续性，因为内容每周都是真实新数据生成的。

## 如果让我打分

**综合：7 / 10**

理由：

- README 写的很好，比很多开源项目强很多，核心卖点说清楚了，表格直观
- 功能设计有想法，"双向桥接"这个切入点确实差异化
- 死亡吐槽 + 定时推送 + 盖房子，这三个是真正抓眼球的功能
- 扣分在部署门槛和 DF 功能的实际数据质量问题

## 3 个最劝退的点

### 劝退 1：QQ 接入那一步，新人必卡（README 第三屏"前置要求"）

README 里写"QQ 桥接（可选）：NapCat / Lagrange / go-cqhttp 之一，OneBot 11 协议，跑在 localhost"。

这句话对我这种玩家来说，就是天书。

NapCat 是什么？OneBot 11 又是什么协议？怎么"跑在 localhost"？

最关键的问题：QQ 桥接是用的哪个 QQ 号？我的 QQ 号还是要申请一个专门的机器人号？如果用我自己的号会不会被封？

这是 99% 的新人会在这一步放弃的地方。QUICK_START.md 里甚至完全没有讲 QQ 接入这一步——它结束在"运行"那里，然后说"进入 Minecraft 服务器在聊天框打字试试"。但 QQ 桥接才是大多数人感兴趣的功能啊，没有这一步，项目一半的卖点白费。

**这是最大的 friction point，没有之一。**

### 劝退 2：DF 模块 cookie 抓包（每隔几天就要重抓）

"cookie 几小时到几天就过期，需要重新抓包。broadcast_hour 时段失败会把错误推到群里提醒。"

这个问题对群主来说是运维负担，对群友来说是"这个 bot 怎么又不好使了"。

抓包这件事，大多数 DF 玩家不会。就算按教程做了，过了两天 cookie 又过期，再抓一次，两天后再过期……这个循环会让人放弃的。

功能再好，维护成本高就是劝退。

### 劝退 3：README 中的术语对非技术用户不友好（README 第四屏"关键约束"）

"AI 在回复里用 `[CMD:...]` 标签发指令，bot 正则提取 → 走 RCON 执行 → 结果回灌给 AI → AI 决定下一步"

这段说的是实现原理，对开发者是有意思的，对我来说是不明觉厉。普通玩家不需要知道这些，但它放在 README 正文里，打乱了阅读节奏，让我以为接下来要看技术文档了，容易劝退。

建议把这块折叠或者挪到"技术细节"部分，主 README 对玩家保持"功能介绍 + 上手指引"风格就够了。

## 3 个真的喜欢的点

### 喜欢 1：截图和功能表设计得很直观

一上来就有截图，然后是功能表格，每行"你说的 → bot 干了什么"，这个格式看完就懂了。没有一上来就甩代码，没有假设我知道所有背景知识，这个做法很对。

特别是 MC 模块那张 AI 盖出来豪宅的截图，视觉冲击力到位，我看完第一反应是"哇这个真的可以"。

### 喜欢 2：不消耗 API 额度的功能单独标出来

README 里写了"附赠（不消耗 API 额度）"下面列了死亡吐槽、加入提醒这些。

这个细节很贴心。大学生部署这个项目，API 费用是很真实的顾虑，明确说哪些功能是"免费跑的"会让人放心很多。

### 喜欢 3：DeepSeek 推荐 + Ollama 备选

支持 Ollama 本地模型是个加分项。如果真的不想花钱买 API，下个 Ollama 跑本地模型也能用，这条退路写出来了很好。

DeepSeek 推荐的"便宜，中文好"，说到点子上了——大学生最在乎这个。
